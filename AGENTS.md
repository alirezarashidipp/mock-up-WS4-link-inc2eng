# Project instructions

Keep the stage-one entry point in `finding.py` at the project root. Use plain functions under `app/finding/`. In `main()`, show the steps for reading each source, selecting incident rows, cleaning names, applying alias replacements, matching and saving.

Preserve original source values in the candidate workbook. Change supplier exceptions in `config/supplier_aliases.yml`. Keep code, definitions, documentation and output labels in English. Update the relevant stage guide in `docs/finding/README.md` or `docs/linking/README.md` when behaviour changes. Keep the stage index in `docs/current-state.md` aligned with both guides.

Incident names follow the rules in `app/finding/clean_incidents.py` and use whole-name YAML aliases. For engagement name comparisons, lowercase the source text and remove whitespace. Match types and column priorities live in `app/finding/match_rows.py`.

Keep the stage-two entry point in `linking.py` and its reader, model decision and CSV writer in `app/linking/`. Read Linking data from `data/output/engagement_candidates.xlsx`. Assess every candidate independently within its incident. Match results by local candidate number and preserve every source row and column in source order in the CSV. Append only the eight fields listed in `app/linking/save_results.py`. Repeat the incident evidence strength across its rows. Several candidates may be LINKED. Mark the sole confirmed link or the uniquely strongest confirmed candidate STRONGEST_LINKED. Keep tied leaders LINKED. Use POSSIBLY_LINKED for unresolved service fits and NOT_LINKED for incompatible or unsupported candidates. Save each incident before requesting the next and resume completed work from the CSV. Verify output changes with synthetic inputs and distinguish offline model-response checks from live provider tests.
