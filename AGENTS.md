# Project instructions

Keep the stage-one entry point in `finding.py` at the project root. Use plain functions under `app/finding/`. In `main()`, show the steps for reading each source, selecting incident rows, cleaning names, applying alias replacements, matching and saving.

Preserve original source values in the candidate file. Change supplier exceptions in `config/supplier_aliases.yml`. Keep code, definitions, documentation and output labels in English. Update the relevant stage guide in `app/finding/docs/README.md` or `app/linking/docs/README.md` when behaviour changes. Keep the project-root `README.md` aligned with both guides. Documentation describes the current project state.

Incident names follow the rules in `app/finding/clean_incidents.py` and use whole-name YAML aliases. For engagement name comparisons, lowercase the source text and remove whitespace. Match types and column priorities live in `app/finding/match_rows.py`.

Keep the stage-two entry point in `linking.py` and its reader, model decision and CSV writer in `app/linking/`. Read Linking data from `data/output/engagement_candidates.csv`. Assess every candidate independently within its incident. Match results by local candidate number and preserve every source row and column in source order in the CSV. Append only the ten fields listed in `app/linking/save_results.py`. Repeat the incident evidence strength across its rows. Use LINKED for defensible evidence from both records, POSSIBLY_LINKED for a concrete service fit with a material barrier to confirmation, NOT_LINKED for evidence that excludes the candidate, and INSUFFICIENT_EVIDENCE for insufficient service-specific information. Select the sole LINKED candidate. With several confirmed links, select up to three only when each has specific evidence placing it among the strongest. If no leaders can be established, or more than three are indistinguishable at the top, select none. Preserve source order and never use it to break ties. Record YES and one sentence of evidence for each selected candidate. Save each incident before requesting the next and resume completed work from the CSV. Verify output changes with synthetic inputs and distinguish offline model-response checks from live provider tests.
